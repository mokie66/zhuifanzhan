### 为什么必须走代理

实测结论（`scripts/` 下的验证脚本可复现）：

| 链路 | CORS 头 | 结论 |
| --- | --- | --- |
| 采集接口（`?ac=list` / `?ac=detail`） | **无** `Access-Control-Allow-Origin` | 浏览器直连被拦，**必须代理** |
| 视频 m3u8 | `Access-Control-Allow-Origin: *` | 可直连 |
| 视频 ts 分片 | `Access-Control-Allow-Origin: *` | 可直连 |

所以只代理 API，不代理视频流——这样服务器带宽压力最小，播放质量最好。

## 三、关键技术决策

### 1. 分类语义归一（解决各源 type_id 不一致）

**问题**：各源的分类编号体系互不相同。

```
源 A：1=电影片   2=连续剧   3=综艺片   4=动漫片
源 B：1=电影     2=电视剧   3=综艺     4=动漫
源 C：7=电影     8=连续剧   9=综艺    40=动漫
```

如果硬编码 `type_id=1` 查电影，在源 C 上会查到完全不相干的内容。

**方案**（`src/api/taxonomy.js`）：读每个源自己的分类表 → 按**名称语义**归一到统一分组
（movie / tv / anime / variety / short / doc / sports）→ 得到该源在此分组下应使用的 id。

判断依据两层，缺一不可：
- **层级**：`type_pid === 0` 是顶级分类，子分类继承父级语义
- **名称**：顶级分类名常带「片」字（电影片 / 综艺片 / 动漫片），需关键词匹配

匹配顺序有讲究：「动漫电影」必须归入动漫而非电影，所以动漫的优先级排在电影之前。

验证结果：**分类翻译准确率 100%**（`scripts/verify-taxonomy.mjs`）

### 2. `t=` 参数是精确匹配（关键发现）

**实测**：

```
量子   t=1（电影片顶级） → total=1      只返回顶级分类自己的占位数据
量子   t=6（动作片子类） → total=4974   正常
非凡   t=1               → total=0      顶级下无任何影片
电影天堂 t=1             → total=0
```

**结论**：`t=` **不包含子分类**。用顶级 id 查询会得到空列表。

因此分两种查询策略（`src/api/index.js`）：

| 策略 | 做法 | 用于 |
| --- | --- | --- |
| A | 不带 `t` 拉取，客户端按分类表过滤 | 曾用于首页；实测 movie 分组只能命中 0~3 条，已弃用 |
| **B** | **用子分类 id 查询，不同源取不同子分类** | **列表与首页统一使用** |

策略 B 的效果：每个分组稳定 20 条/页，且不同源覆盖不同子分类，内容不重复。
分页实现为「子分类轮转」——第 P 页取 `children[(P-1) % n]`，保证分页语义真实。

验证结果：**tv 39 部 / anime 46 部 / movie 42 部，全部可播**（`scripts/verify-flow.mjs`）

### 3. 播放地址的两类线路

资源站通常同时提供：

```
vod_play_from = "liangzi$$$lzm3u8"
                  ↑          ↑
              解析线路     直链 m3u8 线路
vod_play_url  = "第01集$url#第02集$url$$$第01集$url#..."
                   ↑    ↑        ↑
               集名与地址 集之间   线路之间
```

- **解析线路**：地址形如 `https://host/share/<hash>`，需网页解析才能取到流，前端无法直接播
- **直链线路**：地址以 `.m3u8` 结尾，可直接交给 hls.js

`parsePlayUrl()` 解析后给每条线路打 `playable` 标记，播放器**优先选直链线路**；
UI 上明确标注「可播 / 需解析」，不假装解析线路也能播。

### 4. 跨源合并与换源

同一部片常出现在多个源（实测 75 部搜索结果中有 23 部跨源重复）。

- **列表/搜索**：按归一化片名去重，主记录取「线路多 + 集数全 + 源权重高」的那条，
  其余挂到 `mirrors` 上，卡片显示「N 源」角标
- **详情**：用片名到其他源搜索同名片，把它们的线路一并合入 `allLines`，
  于是「换源」功能天然可用

实测：《神印王座》聚合出 **8 条线路（5 条可播）**，来自 4 个不同的源。

### 5. 播放器

`src/components/VideoPlayer.vue`：

- **hls.js** 播 m3u8；Safari / iOS 走原生 HLS，省一层 MSE
- **分级错误恢复**（按 hls.js 官方建议，不直接报错）：
  网络错误 → `startLoad()` 重拉清单；媒体错误 → `recoverMediaError()` 恢复解码；
  仍失败才提示用户换线路
- **进度记忆**：节流 5 秒写 localStorage，暂停与卸载前补写一次；
  已看完（>95%）则不续播，从头开始更符合预期
- **播完自动下一集**
- **混合内容兜底**：`http://` 资源在 `https://` 页面下会被拦，
  由 `utils/media.js` 的 `resolvePlayUrl` 自动套 `/collect/_stream` 代理
- 倍速、音量、全屏、拖拽进度、缓冲条

### 6. 路由带参数

```
/detail/:sourceKey/:id                  详情（可分享、刷新不丢状态）
/player/:sourceKey/:id/:episodeIndex    播放（?line=<lineKey> 指定线路）
/tv /anime /movie /variety              分类库（共用 BrowseView，meta.group 区分）
/browse/:group                          通用分类入口，便于扩展
```

`sourceKey` 进 URL 是必要的：同一部片在不同源有不同 id，只有 id 无法定位。

## 五、生产部署

### 1. 构建

```bash
npm run build       # 产物在 dist/
```

### 2. 生成 nginx 采集源代理配置

```bash
node scripts/gen-nginx.mjs     # 输出 deploy/nginx-collect.conf
```

配置从 `src/api/sources.js` 自动生成，避免手写配置与源列表脱节。

### 3. 完整 nginx server 块示例

```nginx
server {
    listen 443 ssl http2;
    server_name your-domain.com;

    ssl_certificate     /etc/nginx/ssl/fullchain.pem;
    ssl_certificate_key /etc/nginx/ssl/privkey.pem;

    # 前端静态资源
    root /var/www/personal-media-vue;
    index index.html;

    # SPA 路由回退（history 模式必须）
    location / {
        try_files $uri $uri/ /index.html;
    }

    # 采集源反向代理（内容来自 deploy/nginx-collect.conf）
    include /etc/nginx/conf.d/nginx-collect.conf;

    # 静态资源缓存
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;
}
```

### 4. 部署检查清单

- [ ] `include` 的 nginx-collect.conf 路径正确
- [ ] 站点启用 HTTPS（否则 `encodeURIComponent` 的流代理无意义，且部分源在 http 下也不安全）
- [ ] nginx 配置里用了 `resolver`，需确认 DNS 可用（默认写了阿里/腾讯的公共 DNS）
- [ ] 若服务器在国内，建议对采集源做一次连通性复检（源站常对海外 IP 限流）
- [ ] `dist/assets/` 缓存策略生效，但 `index.html` 不要长缓存

## 六、已知限制（如实说明）

1. **解析线路不可播**：约一半线路是网页解析型（`/share/<hash>`），需要额外的解析器组件。
   当前 UI 会明确标注「需解析」并优先选直链线路，不会误导用户。
   <br>要支持这类线路，需要接入对应源站的解析规则或第三方解析服务，属于后续工作。

2. **分页是近似语义**：多源聚合下各源每页条数不同，无法严格对齐。
   当前实现是「子分类轮转 + 合并」，页码语义稳定但不是绝对连续的全局分页。

3. **源稳定性**：采集源域名更换频繁、会限流、会关站。
   已做多源冗余 + 单源失败不影响整体 + 首页展示源健康状态，
   但源本身的质量需要长期运维。

4. **用户体系未接入**：收藏 / 历史 / 进度存在 localStorage。
   `utils/storage.js` 的接口全部是 Promise，将来换成 HTTP 调用时视图层无需改动。

5. **天涯源不支持搜索**：其搜索接口返回「暂不支持搜索」纯文本而非 JSON。
   聚合层会把它标记为失败源并跳过，不影响其他源。

6. **未做 SSR/SEO**：纯客户端渲染，搜索引擎抓不到内容。
   如需要 SEO，应引入 Nuxt 或做预渲染。
